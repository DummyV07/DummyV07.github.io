数据库

发表于2026-10-28|更新于2026-10-28|工程实践
|总字数:4.4k|阅读时长:13分钟|浏览量:

数据库按「里面存的是什么、查询时怎么找」来分，比按厂商名单来分更不容易过时。DBX（轻量数据库工作台）的新建连接就是按这个习惯分组的：关系型、分析型、文档键值与搜索、图与向量、时序，旁边再放消息队列和注册配置。同一类里会打开相近的工作区，换一类就换一套对象，而不是所有系统都挤进一个 SQL 输入框。

本文按这套分类做综述。每一类先说明数据长什么样，再写经典产品各自站在哪。最近业务里用到的 PostgreSQL（关系型数据库）和 InfluxDB（时序数据库）作为这两类的案例，多记一层对象模型和查询语言。

1. 七类放在一张表里

类别 一条数据是什么 查询时在找什么 经典产品
关系型与兼容协议 有类型的一行 事务、关联、按条件更新 PostgreSQL、MySQL、SQLite、Oracle、SQL Server
分析型与数据仓库 用来扫描的大批量行或列 聚合、多维分析、跨源查询 ClickHouse、Doris、StarRocks、Snowflake、BigQuery、Trino
文档、键值与搜索 一篇文档、一个键，或一段可检索文本 按键取值、按字段取文档、全文检索 MongoDB、Redis、Elasticsearch、Cassandra、HBase
图、向量与 AI 数据 点和边，或一组高维向量 沿关系游走，或找最相近的向量 Neo4j、Milvus、Qdrant、Weaviate、ChromaDB
时序系统 时间戳加上维度和数值 一段时间里的趋势、降采样 InfluxDB、TDengine、IoTDB、QuestDB
消息队列 一条待传递的事件 谁生产、谁消费、能不能回放 Kafka、RabbitMQ、RocketMQ、Pulsar
注册与配置中心 一个会被监听的键 配置当前值、服务有没有在线 etcd、ZooKeeper、Nacos

前五类是数据库的主体。后两类在新建连接里和库排在一起，因为排障时经常要从表跳到消息，再跳到配置；它们保存的是事件流和协调数据。

还有一条不单独构成数据模型：驱动扩展。JDBC（Java Database Connectivity，Java 数据库连接）、厂商私有驱动、MySQL / PostgreSQL 协议兼容，解决的是「这个引擎怎么连上」。达梦、Snowflake、Hive 很多走这条路。能连上，只说明协议通了，系统表、权限和高级功能仍以该引擎自己的为准。

2. 关系型与兼容协议

关系型数据库把数据放进表。每一列有类型，每一行是一条记录，表和表用键关联。查询语言是 SQL，写入用事务包起来：同一笔业务里的多次修改一起成功，或一起回到原样。这类系统承载在线交易（OLTP，联机事务处理），用户、订单、库存、权限都在这里。

经典产品可以按出现的场景记：

产品 常见位置 记一点就够的特征
Oracle 传统企业核心库 商业支持完整，过程语言是 PL/SQL，端口常见 1521
SQL Server 微软技术栈 方言是 T-SQL，和 Windows、.NET 一起出现，端口常见 1433
MySQL 网站和互联网业务 长期是 Web 应用的默认选择，存储引擎以 InnoDB 为主，端口 3306。MariaDB 是它的分支，TiDB、OceanBase 则用 MySQL 协议做分布式
SQLite 手机、桌面、嵌入式、单机工具 整个库是一个文件，没有独立的数据库服务进程
达梦、openGauss、GaussDB 国产化和政企项目 达梦靠近 Oracle 的使用习惯；openGauss、GaussDB 沿 PostgreSQL 演进而来。协议或语法兼容，不等于系统表和运维命令可以照搬

案例：PostgreSQL

PostgreSQL 把 SQL 标准、扩展和复杂类型放在同一套引擎里，默认端口 5432。业务库、地理数据（PostGIS）、向量（pgvector）、时序（TimescaleDB）都能以扩展的形式长在它上面，所以它经常是「先上一套关系库，再看要不要拆出去」的那套。

库里面的对象可以这样对应：

对象 含义
database（数据库） 一套独立的数据空间，连接时要写明名字
schema（模式） 库内的命名空间，默认是 public
table / view 表存数据，视图把常用查询固定下来
role（角色） 登录和授权的主体

真正写业务时有三件容易踩错：

  • 时间列用 timestamptz，入库时按统一时刻保存。不带时区的 timestamp 会把「服务器在哪个时区」卷进数据里。
  • 会参与约束和对账的列用独立字段；形状经常变的附属信息用 jsonb。jsonb 是二进制 JSON，可以建 GIN 索引。
  • 一次业务动作放进一个事务。PostgreSQL 用 MVCC（多版本并发控制）让读和写少互相阻塞，没提交的长事务会拖住旧版本的清理。

生产查询用单独的只读角色。索引按查询建：等值、范围和排序用 B-tree，jsonb 和全文用 GIN。

3. 分析型与数据仓库

分析型系统为一件事优化：一次读进很多行，算出合计、分位数和趋势。数据往往从关系库、日志或消息队列同步过来，分析查询允许秒级甚至更久，换来的是扫描和聚合的吞吐。习惯上把这类负载叫 OLAP（联机分析处理）。

产品 它经典在哪
ClickHouse 列式存储。同一列的值放在一起，对事件明细做过滤和聚合很快，适合日志、点击、账单明细
Doris、StarRocks 实时分析库，对外提供 MySQL 协议。已有的 SQL 客户端和 BI 工具容易接上来
Snowflake、BigQuery 云上的数据仓库。存储和计算分开，按使用的计算资源计费，适合把各业务的表汇总成分析层
Databricks 湖仓一体。数据以数据湖里的文件为底（常见是 Delta Lake），上面用 Spark SQL 做分析和机器学习
Trino 分布式查询引擎。自己通常不作为主存，而是用 SQL 同时查 Hive、Iceberg、PostgreSQL 等多个数据源

关系库里的一张订单表，和分析库里的一份订单明细，可以并存。前者负责下单时的正确性，后者负责「过去 30 天各省的支付金额」。分析库里的行可以晚到几秒或几分钟，这个延迟要在业务上接受。

4. 文档、键值与搜索

这一类不把「一张事先定好的表」当作唯一模型。DBX 把它们放在同一组，是因为连接之后进入的是文档、键、索引或列族浏览器，而不是关系库那套表结构编辑器。里面其实是四种经典模型。

4.1 文档数据库

一条记录是一篇文档，通常是 JSON 或 BSON。不同文档的字段可以不一样。

  • MongoDB 是这类里最常见的产品，端口 27017。查询用自己的查询语言和聚合管道，适合内容、活动配置、字段经常加减的档案。
  • CouchDB 把文档暴露成 HTTP 接口，强调多主复制，适合需要离线同步的场景。

订单金额、库存这种要对账的数据，仍适合放在关系库。文档库存「这一份内容长什么样」。

4.2 键值数据库

按一个键取对应的值，路径短，延迟低。

Redis 是经典实现，端口 6379。值可以是字符串、哈希、列表、集合、有序集合。它常年待在内存里，用来做缓存、会话、计数器和分布式锁；RDB 和 AOF 用来把内存数据落到磁盘。Redis 也可以挂模块做搜索或向量，那是在键值引擎上长出来的能力。

4.3 宽表与列族

行键决定数据落在哪台机器上，列可以很宽，也可以按列族分组。

  • Cassandra 没有单独的主节点，写入路径短，适合全球分布、写入量很大的数据。查询要带上分区键，否则就变成扫全集群。
  • HBase 跑在 Hadoop 生态上，按行键和列族组织，适合超大的稀疏表，例如历史归档和画像的宽表。

4.4 搜索引擎

Elasticsearch 为全文检索和日志检索而做，端口常见 9200。文本被拆成词项，建成倒排索引，再配合过滤和聚合。OpenSearch 是同源的另一条产品线。Meilisearch 更轻，常用于站内搜索。

搜索索引一般是派生数据。文章正文、订单状态留在主库，搜索引擎保存一份为了「搜到」而建的索引，主库更新后再同步过去。

5. 图、向量与 AI 数据

关系库用 join 表达联系。当联系本身就是查询对象，或者要找的是「和这段内容最像的记录」时，会换成图或向量。

5.1 图数据库

图由节点和边组成，边可以带类型和属性。查询是在图上走若干步。

Neo4j 是属性图的经典产品，查询语言是 Cypher。人物关系、欺诈团伙、依赖链路，用「从某个节点出发，沿某类边走 N 步」来写，比多层 join 更直接。图库存的是关系网络；节点上的主档资料往往还在关系库里有一份。

5.2 向量数据库

向量库存的是嵌入（embedding）：把文本、图片或音频变成一组高维浮点数。查询是相似度搜索，距离越近越相近，常用余弦、点积或欧氏距离。为了在亿级向量里仍能返回，引擎使用近似最近邻索引。

产品 常见用法
Milvus 面向大规模向量的开源库，支持稠密向量、稀疏向量和混合检索，常用于检索增强生成（RAG）和推荐
Qdrant 向量和标量过滤放在一起，适合「先按租户或标签圈定，再在圈里找相似」
Weaviate 向量库带模块生态，方便把向量化和检索接在一条链路里
ChromaDB 轻量，常嵌在本地或原型级的 AI 应用里
pgvector PostgreSQL 扩展。向量规模还没大到要独立集群时，可以和业务表放在同一个库

Milvus 一类系统里，稠密检索看语义，稀疏检索看关键词，混合检索把两边的结果合在一起。衡量效果时看召回率（返回的前 K 条里有多少真正相关）和每秒查询数（QPS）。索引和参数要跟着数据和延迟要求走，这里不展开具体算法。

6. 时序系统

时序数据库存按时间排列的点：一个时间戳、若干用来过滤的维度、若干数值。监控指标、设备采样、接口耗时都属于这一类。写入是追加，更新很少，查询几乎都带时间范围，原始数据过一段时间就会被降采样或删掉。

产品 常见用法
InfluxDB 通用时序库，监控和业务指标都能放，写入用行协议
TDengine 面向物联网，按设备超级表建模，SQL 味道更重
IoTDB Apache 项目，面向工业设备的测点，强调高写入和按设备组织
QuestDB 用 SQL 查询时序，也能接收 Influx 的行协议，适合希望少学一种查询语言的场景
TimescaleDB PostgreSQL 上的时序扩展。数据量还没迫使你再维护一套引擎时，可以留在关系库里
Prometheus 监控系统自己的时序库，拉取指标，查询语言是 PromQL。它和 Grafana 那条链路绑得更紧，见《Grafana生态》

案例：InfluxDB

InfluxDB 的默认端口是 8086。一条点用 Line Protocol（行协议）写成四段：度量名、标签、字段、时间戳。

部分 含义
measurement（度量） 这组点的名字，接近「表」，这里是 api_request
tag（标签） 用来过滤和分组的维度，会建索引，这里是 app、path
field（字段） 实际数值，默认不按它建索引，这里是 latency_ms、status_code
timestamp（时间戳） 点发生的时刻，行协议里通常是纳秒

标签只放取值有限的维度，例如应用、接口、机房。用户 id、订单号、trace id 放进标签会让索引膨胀。这些高基数的标识留在 PostgreSQL，时序这边保留能聚合的数字。

版本决定连接方式和查询语言，三者不能混用：

版本 怎么组织数据 认证 查询
1.x database + retention policy（保留策略） 用户名和密码 InfluxQL，接近 SQL
2.x organization + bucket（桶） API token 主路径是 Flux，部分接口仍接受 InfluxQL
3.x 以表为中心，写入仍可用行协议 token SQL 和 InfluxQL

7. 消息队列

消息队列保存的是已经发生、等待被消费的事件。它保证传递、堆积和回放，不负责事务型的主数据。

产品 模型 经典场景
Kafka 按主题追加的提交日志，消费者自己记住读到哪 日志采集、事件流、把业务库的变更同步到分析库
RabbitMQ 交换机按路由键把消息送进队列 任务分发、延迟要求不高的业务消息
RocketMQ 主题、队列和消费组，国内业务里常见事务消息 订单、支付链路里的异步解耦
Pulsar 计算和存储分开，主题可以再分成租户和命名空间 多租户的消息平台

在 DBX 里，这类连接打开的是主题、订阅或消费者、消息和权限，而不是表。看一条业务为什么「库里有了、下游还没动」，就要同时看关系库和这里的消费进度。

8. 注册与配置中心

这一类保存会被别人监听的小数据：配置项、谁是主、服务实例还在不在。数据量通常不大，一致性和变更通知比扫描更重要。

产品 经典场景
etcd 带租约和监听的键值存储，Kubernetes 用它保存集群期望状态
ZooKeeper 用 ZNode 做协调，Hadoop、Kafka 的老架构里用它选主和存元数据
Nacos 配置管理和服务注册发现，常见于国内的微服务
Consul 服务发现加上 KV，配置和健康检查放在一起

配置中心的值会热更新到进程里。它替代不了数据库里的业务记录：开关和连接地址放这里，订单放 PostgreSQL。

9. 选一类，再用同一个工作台看

选型时先对上表里的「一条数据是什么」：

  1. 要更新、要对账、要和别的表一起读，用关系型。业务主库优先 PostgreSQL 或 MySQL 这一档。
  2. 要对数百万行以上做汇总，把明细同步到 ClickHouse、Doris 或云数仓。
  3. 字段经常变、按键读取、或要全文搜索，分别看文档、Redis 和 Elasticsearch。
  4. 关系网络用图；语义相似用向量。规模不大时，向量可以先用 pgvector。
  5. 按时间追加、会过期的指标用时序库。监控链路里 Prometheus 已经够用时，不必再叠一套 InfluxDB。
  6. 异步解耦用消息队列，动态配置用 etcd 或 Nacos。

DBX 的新建连接按上面的类别列引擎，源码在 t8y2/dbx。关系型和分析型进入 SQL 编辑器、结果网格和表结构；文档、键值、搜索、向量、时序、消息队列、配置中心进入各自的专项工作台。桌面端适合人每天查看，Docker / Web 适合放到服务器上用浏览器打开，命令行和 MCP（Model Context Protocol，模型上下文协议）适合脚本和编码助手复用已经配好的连接。

PostgreSQL 在命令行里可以直接查。InfluxDB 在当前 CLI 里需要桌面端桥接，以本机 dbx capabilities 为准。2.x 要填 organization 和 token，1.x 用用户名、密码和 database。3.x 是否可连，看所安装的 DBX 版本。

生产连接打开只读或生产保护。数据库账号的权限是最后边界，客户端拦不住一个本来就拥有写权限、又绕过客户端的会话。小库可以用 DBX 的导出做迁移，生产备份用数据库自己的工具。

10. 小结

  • 数据库大类按数据模型和查询方式分：关系型、分析型、文档键值与搜索、图与向量、时序。消息队列和注册配置是新建连接里相邻的两类数据系统。
  • 每一类都有停留多年的经典产品。MySQL 和 PostgreSQL 承担在线业务，ClickHouse 和云数仓承担汇总，MongoDB、Redis、Elasticsearch 分别承担文档、缓存和检索，Neo4j 和 Milvus 承担关系和相似度，InfluxDB 与 Prometheus 承担时间序列。
  • 一套业务通常同时用到其中几类。主数据在 PostgreSQL，趋势在 InfluxDB，搜索、缓存、消息和配置各用各的产品，再用 DBX 这种按类别打开工作区的客户端把它们看全。
